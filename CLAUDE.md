## What This Is

A local RAG chatbot for the Magic Garden game, designed to run entirely on a Mac Mini M4 (16GB RAM). Uses Ollama for embeddings (nomic-embed-text) and generation (Mistral 7B), ChromaDB for vector storage. All game data is extracted from the game client JavaScript source code, stored in `data/source_truth.json`.

## Commands

```bash
# Setup (first time)
chmod +x scripts/setup.sh && ./scripts/setup.sh

# Or manual setup
python3.12 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
ollama pull mistral:7b-instruct-v0.3-q4_K_M
ollama pull nomic-embed-text

# Data pipeline (run in order after source_truth.json changes)
python scripts/generate_chunks.py    # source_truth.json → data/chunks/*.json
python scripts/index_chunks.py       # chunks → ChromaDB (requires Ollama running)

# Run
python scripts/chat.py                                      # Interactive CLI
uvicorn api.server:app --host 0.0.0.0 --port 8000          # API server

# Tests (no Ollama required)
python -m pytest tests/ -v
python -m pytest tests/test_core.py -v -k test_diet_intent  # Single test
```

## Architecture

The pipeline processes one query per turn with exactly **1 LLM call** (generation only). Everything else is deterministic Python:

```
User Query → EntityRegistry (regex) → QueryAnalyser (intent detection + query reformulation)
           → VectorStore (ChromaDB filtered retrieval) → Context Assembly (token-budgeted)
           → LLM generate (Mistral 7B via Ollama) → Response
```

### Key modules in `src/`

- **`entity_registry.py`** — Bidirectional name resolution between player-facing display names and game source internal IDs (e.g., "Amberbound" ↔ `Ambercharged`). Uses a pre-compiled regex sorted by key length descending so multi-word entities like "fire horse" match before "horse". The `_REGISTRY` dict and `INTERNAL_TO_DISPLAY` dict are the canonical name mappings.
- **`query_analyser.py`** — Detects intent via regex patterns (`_INTENT_PATTERNS`) and constructs an embedding query by combining entity display names with intent keywords. Supports carry-forward entities from conversation state for pronoun resolution.
- **`bot.py`** — `MagicGardenBot.answer()` orchestrates the full pipeline. Falls back to unfiltered retrieval if metadata-filtered ChromaDB query returns nothing. `debug_answer()` returns the same result plus retrieval diagnostics.
- **`vector_store.py`** — Wraps ChromaDB with Ollama embedding calls. Embeds in batches of 50. Retrieval filters by metadata (entity_type) and applies a cosine similarity threshold (0.30).
- **`conversation_state.py`** — Tracks entities across turns for follow-up queries. Carry-forward expires after 3 turns without a new entity mention.

### Chunk layers (generated by `scripts/generate_chunks.py`)

1. **Entity** (~170 chunks) — One per game entity (pets, crops, abilities, mutations, weather, eggs, tools)
2. **Relationship** (~60 chunks) — Diet chains, crop feeders, ability families, weather combos, multiplier guide
3. **Summary** (~6 chunks) — Pets by egg, crops by rarity, hunger costs, sell values, harvest comparison
4. **Strategy** (4 chunks) — Early game, income, pet loadouts, journal completion

### API (`api/server.py`)

Single POST endpoint `/ask` with session-based conversation state. Sessions are in-memory dicts keyed by `session_id`.

## Internal vs Display Name System

The game source uses internal IDs that differ from player-facing names. This mapping is critical and duplicated in two places that must stay in sync:
- `src/entity_registry.py` — `_REGISTRY` and `INTERNAL_TO_DISPLAY`
- `scripts/generate_chunks.py` — `CROP_DISPLAY` and `PET_DISPLAY`

Examples: `Ambercharged` → "Amberbound", `OrangeTulip` → "Tulip", `WhiteCaribou` → "Caribou", `Frost` → "Snow"

## Config (`src/config.py`)

All tunable parameters: model names, retrieval limits (6 chunks, 1200 token context budget, 0.30 similarity threshold), generation settings (temperature 0.1, 300 max tokens), conversation carry-forward window (3 turns).
